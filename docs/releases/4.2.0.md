# ArkGate 4.2.0

- **Status:** prepared
- **npm:** `arkgate@4.2.0` (not published yet)
- **Git tag:** `v4.2.0` (pending)

**Minor** over **4.1.1**. Phase WI fixes the recurring wrong-project MCP failure and makes
same-machine multi-repository installation deterministic.

No required config migration. Codex remains advisory at write time; the required CI status is
still the hard merge boundary. Legacy MCP calls remain compatible but non-authoritative until the
caller binds the expected workspace.

## Why the MCP fix is durable

Start each project with its own project-scoped MCP process. Before trusting any Ark result:

```json
{
  "tool": "ark_identity",
  "arguments": {
    "project": {
      "expectedRoot": "/absolute/exact-project-root"
    }
  }
}
```

Trust the process only when `binding.status` is `matched` and `authoritative` is `true`. Reuse the
returned `projectIdentity.projectId` together with `expectedRoot` on later calls, then read the
contract with:

```json
{
  "tool": "ark_manifest",
  "arguments": {
    "project": {
      "expectedRoot": "/absolute/exact-project-root",
      "expectedProjectId": "sha256:returned-by-ark-identity"
    }
  }
}
```

The initial handshake requires the exact project root. A contained descendant is authoritative
only when the matching project id is also supplied. A mismatch fails before project placement,
golden-pattern, Layers, or ArkRules analysis. A missing identity or manifest tool means the host
still has an older process; restart it and use the workspace-local CLI meanwhile.

`ark://manifest` remains available for compatibility with standard MCP `resources/read`, but it
is always `unverified` and non-authoritative because that request cannot portably carry the
project expectation.

`projectId` identifies the canonical local root and config. It survives process restarts and
contract edits, but is intentionally not equal across machines or operating systems.

## Several repositories on one machine

- `.agents/skills`, `.claude/skills`, `.grok/skills`, and other repo catalogs remain isolated in
  their repository and follow that repo's installed package.
- An upgrade does not rewrite a skill when only its generated `arkVersion` stamp differs.
- Optional `$CODEX_HOME/skills` is shared. A repo pinned to an older ArkGate cannot downgrade a
  newer managed home skill, even with `--force`.
- `.arkgate-catalog.json` plus an install lock makes the full shared catalog monotonic under
  concurrent installs. Before any skill change, `.arkgate-catalog.pending.json` durably records
  the incoming version as a monotonic floor; if catalog commit is interrupted, an older repo
  remains blocked and a same/newer retry completes and ownership-safely clears the journal.
  Corrupt catalog or journal metadata blocks mutation fail-safe.
- A newer catalog removes a retired skill only when it is still exactly Ark-managed; customized
  retired content is preserved and released from ownership.
- Identical content is a no-op; preserved custom content still follows the explicit replacement
  contract.
- Skills route a workflow. They do not select the MCP project; `ark_identity` binds it and
  `ark_manifest` reads its authoritative contract.

## Upgrade

```bash
npm install -D arkgate@4.2.0
npx arkgate-check --doctor --json
```

For Codex, confirm the repository `.codex/config.toml`, restart Codex, then run the identity
handshake above. The setup JSON remains conservative because it cannot observe a later live MCP
conversation.

No `ark.config.json` migration is required. Dual bins `arkgate*` / `ark*` are unchanged.

HTML evolution reports keep their raw origin/current facts across upgrades, but show `—` instead
of a score delta when the two snapshots name different ArkGate versions. Each new snapshot also
records best-effort Git provenance (`HEAD`, attached branch, and dirty-worktree state); outside a
Git worktree the evidence is explicitly unavailable.

## Compatibility and limits

- Existing MCP clients remain callable but receive `binding.status = "unverified"` and
  `authoritative = false` until they send the expectation.
- Standard `ark://manifest` resource reads remain callable but always unverified; authoritative
  contract discovery uses `ark_manifest`.
- Codex/Cursor/OpenCode are still advisory at local write time.
- The release does not add automatic MCP retargeting, cross-machine identity, new architecture
  presets, runtime-kernel features, or a numeric architecture score.
- Z09 / RB-11 retained-adoption and independent-close claims remain open.

## Security notes

The identity expectation is validated before project-specific analysis. Absolute tool paths,
config inputs, symlinks, and nested projects cannot select or escape the process's bound root.
Identity proves which advisory process answered; it does not claim that every local write passed
through Codex MCP.
